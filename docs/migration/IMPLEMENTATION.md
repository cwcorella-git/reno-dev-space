# Implementation Process

Process decisions for the implementation phase, captured 2026-05-20. Separate from the design docs (which are architecture) — this doc covers *how* we build, not *what* we build.

## Stack decisions for the Worker

### Query layer: Drizzle ORM

- Type-safe schema-first ORM. Schema lives in `workers/src/db/schema.ts` as TypeScript objects; SQL `CREATE TABLE` statements are generated by drizzle-kit, not hand-written.
- Bidirectional source-of-truth question resolved: **TypeScript schema is canonical**; `SCHEMA.md`'s SQL is the design reference and the migrations land via drizzle-kit.
- Bundle cost: ~5MB added to the Worker. Well under the 10MB Worker limit.
- D1 driver: `drizzle-orm/d1` adapter.
- Migrations: `npx drizzle-kit generate` produces `workers/migrations/*.sql`; `wrangler d1 execute --remote --file=...` applies.

### Validation: Zod

Every Worker route validates input via Zod schemas before touching D1. Pattern:

```ts
import { z } from 'zod';

const CreateBlockSchema = z.object({
  x: z.number().min(0).max(110),
  y: z.number().min(0),
  width: z.number().min(0).max(100),
  height: z.number().min(0).max(100),
  content: z.string().max(10000),
  style: TextStyleSchema,
});

app.post('/api/canvas', zValidator('json', CreateBlockSchema), async (c) => {
  const body = c.req.valid('json');
  // ... use body with full type safety + validated bounds
});
```

Closes the validation-gap from `STORAGE.md` (file metadata) and replaces what Firestore rules half-enforced via untyped client-side checks.

### HTML sanitization: DOMPurify (server-side via JSDOM or `isomorphic-dompurify`)

Canvas block `content` is rendered as HTML in the client (the rich-text editor allows bold/italic/links). Currently sanitized client-side via `src/lib/sanitize.ts`. After migration, sanitize **also on the Worker** at write time — defense in depth, since a malicious client could bypass the client-side scrub.

Resend templates render whatever HTML the EmailsPanel saves — those are admin-edited so trust-on-write is acceptable, but consider sanitizing on the admin-template POST route too. Defer to security pass.

### Router: Hono

Already decided in `FUNCTIONS.md`. No change.

### Logging: `wrangler tail` + Cloudflare Workers Logs (free)

Built-in. No Sentry yet — add post-cutover if needed.

## Branch & PR strategy

### Single long-lived branch with incremental PRs

```
main
  │
  └─ feat/cloudflare-migration ←── PRs target here, not main
       ├─ feat/cf-mig-01-worker-skeleton
       ├─ feat/cf-mig-02-auth
       ├─ feat/cf-mig-03-realtime-canvas
       ├─ feat/cf-mig-04-realtime-rest
       ├─ feat/cf-mig-05-stripe-port
       ├─ feat/cf-mig-06-email-port
       ├─ feat/cf-mig-07-storage-port
       ├─ feat/cf-mig-08-frontend-swap
       └─ feat/cf-mig-09-import-script
```

- Each sub-PR is small (<500 LOC ideally), focused on one subsystem.
- Sub-PRs merge into `feat/cloudflare-migration`, not `main`.
- Cloudflare Pages auto-generates a preview deploy from the branch — that's where the integration testing happens.
- When everything is green, **a single merge from `feat/cloudflare-migration` → `main` is the cutover commit.** This is Phase 2.2 in `CUTOVER.md`.
- Clean revert if anything goes wrong: revert that single merge commit and `main` is back to Firebase.

### Commit convention

Match the existing repo's pattern (per recent commits like `52fdc3b refactor: extract deriveVoterState()`):
- `feat(migration): ...` for new code paths
- `chore(migration): ...` for infrastructure (wrangler.jsonc, drizzle config)
- `docs(migration): ...` for doc updates as decisions evolve

Sub-PRs squash to a single commit on the migration branch — keeps the eventual cutover diff readable.

## Local dev workflow

### `wrangler dev` + local D1

```bash
# One-time setup per machine
cd workers
wrangler d1 create reno-dev-space         # capture the ID, paste into wrangler.jsonc
wrangler d1 execute reno-dev-space --local --file=./migrations/0001_initial.sql

# Daily loop
cd workers && wrangler dev --persist-to=.wrangler/state  # :8787
cd ..       && npm run dev                                # :3000
```

Frontend talks to the local Worker via `NEXT_PUBLIC_API_BASE=http://localhost:8787` in `.env.local`. Production drops the env var (same-origin routing on `renodevspace.org`).

`.wrangler/state` is gitignored; local D1 persists between runs so test data survives reloads.

### When to deploy to preview

- After each sub-PR merges to `feat/cloudflare-migration`, Cloudflare Pages auto-builds the preview deploy.
- For Worker changes, run `wrangler deploy` manually (Workers don't auto-deploy from git unless we set up Workers Builds — and we explicitly chose not to, per the earlier MIGRATION.md decision).
- Cross-subsystem testing (e.g. testing the canvas DO against a real D1) happens on the preview, not locally — DO behavior diverges between local mocks and real Cloudflare infrastructure.
